# JEV 落地方案（2026-09-20）

> 目标：把假设链的「证据 × 假设」判定从通用大模型下沉到专用决策模型，
> 解决 ACH 诊断 45 秒/条的吞吐瓶颈与 LR 伪概率问题。

---

## 0. 前提修正：中文能力是「未验证」，不是「已知不行」

官方原文（`docs.typesafe.ai/models.md` § Language support）：

> English is the primary training language and where accuracy is currently best.
> Other languages, including CJK scripts, **are handled but not equally well**;
> **test on your own content before relying on Jev for a non-English workload**,
> and pay close attention to Confidence when routing.

三点结论：

1. 官方**承认** CJK 精度更差 —— 你的判断方向正确。
2. 但措辞是 "handled but not equally well"，**不是 "unusable"**。
3. 官方明确要求「用自己的数据测」—— 这正是本方案 Phase 0 要做的。

**为什么不能跳过测试直接做本地复刻：**

你的 ACH 判定是**窄域语义相关性判断**（「这条情报与这个假设是否相关」），
不是通用中文理解。而 JEV 官方宣传的强项恰好是 common-sense judgment。
非母语模型在窄域任务上可能够用 —— 这是**可测的**，测试成本约几美分。

反过来说：本地复刻需要你**先有足够训练数据**（见 §3.1），而你现在只有 219 条
有效 C/I 样本。跳过 Phase 0 直接复刻，等于用最贵的路径赌一个可以用 1 小时证伪的假设。

## 1. 关键认知：这是三层架构，不是模型替换

JEV 只能做决策，不能生成文本。接入它的本质是**把现有调用拆成三层**：

| 层 | 职责 | 现在 | 接入后 |
|---|---|---|---|
| **决策层** | C/I/N 判定、相关性门控 | mimo（45s/条，伪概率） | JEV 或本地复刻（70ms~500ms，校准概率） |
| **生成层** | note 理由、周报、翻译、四维分析 | mimo / nemotron | **不变**（JEV 架构上做不了） |
| **代码层** | LR 计算、贝叶斯更新、阈值判断 | 部分在 AI 里 | **全部下沉到代码** |

**第 3 层是最容易被忽略、但价值最大的一层。** 官方 jaggedness 文档明确列出：

> Jev is not a calculator. We strongly recommend implementing any mathematical logic in code.
> It does not count reliably... Keep the arithmetic in code.

而当前 prompt 直接向模型索取 `"lr": 1.0`（`ach_matrix.py:129`）——
**这是设计错误**。LR 是数值计算，应该由 C/I/N 的概率在代码里推导，不该问模型。

## 2. 必须先做的改造（与接不接 JEV 无关）

这三项改造**本身就有价值**，即使最后不接 JEV 也该做。

### 2.1 拆问题：8 个独立判断，不是 1 个复合判断

**现状**（`ach_matrix.py:123-131`）：一次请求问 8 个假设的 C/I/N + LR + note。

**问题**：复合问题违反 JEV 的 parallel-and-independent 设计，
且官方 jaggedness #8 明确指出「Ask each decision one way」。

**改造后**：一次请求发 8 个独立问题（共享同一个 state），
每个假设一个问题，代码收集 8 个答案。

```python
# 伪代码：JEV 原生形态
questions = {
    f"hyp_{h['id']}": Noul(
        instructions=f"这条情报与假设「{h['title']}」的预期是否一致？"
                     f"证伪判据：{h['falsification']}"
    )
    for h in majors
}
# 一次请求，8 个答案并行返回
```

### 2.2 LR 下沉到代码

**现状**：模型直接吐 `lr` 数值。

**改造后**：模型只给 C/I/N 的**概率**，LR 在代码里算：

```python
# P(证据|假设) / P(证据|非假设) 由概率推导，不由模型口报
CODE_TO_LR = {"C": lambda p: 1.0 + p * 0.8,   # p∈[0,1] → LR∈[1.0, 1.8]
              "I": lambda p: 1.0 - p * 0.7,   # → LR∈[0.3, 1.0]
              "N": lambda p: 1.0}
```

好处：LR 不再是模型拍的伪数值，而是**校准概率的函数**，
可直接进 `calibration.py` 的 Brier 管道。

### 2.3 两段式门控：先判相关性，再判方向

**现状**：93% 的判定结果是 N（实测 3104 条中 2885 条 N）。
这说明**大部分「证据 × 假设」组合根本不该被诊断** —— 当前设计在浪费算力。

**改造后**：

```
第一段 Noul: 「这条情报与该假设相关吗？」→ 概率 < 阈值直接跳过
第二段 Choice: 仅对相关的组合判 C/I
```

收益：诊断量下降、信噪比上升、成本下降。
这一项**不依赖 JEV**，现在就能做。

## 3. Phase 0：前提验证（1 天，成本 < $0.01）

**这是决策闸门 —— 决定走 API 还是走本地。**

### 3.1 步骤

| # | 动作 | 具体 |
|---|---|---|
| 1 | 申请 key | `console.typesafe.ai/keys`（官方 early access，文档齐全，SDK 在 PyPI: `typesafe-sdk` 0.7.0） |
| 2 | 加白名单 | `local/analyze.py:17` 的 `AI_ALLOWED_HOSTS` 加 `api.typesafe.ai` |
| 3 | 写探针脚本 | 新建 `tools/jev_probe.py`：取历史证据 → 调 JEV → 对比 mimo 判定 |
| 4 | 取样 | 从 `ach_matrix.json` 的 388 条证据中，取 **全部 219 条非 N 样本** + 随机 50 条 N 样本 |
| 5 | 跑对比 | JEV vs 现有 mimo 判定，逐条比对 |

### 3.2 评估指标

| 指标 | 说明 | 门槛 |
|---|---|---|
| **C/I 一致率** | 仅在非 N 样本上算（N 占 93%，混入会掩盖问题） | > 80% 可用 / 60-80% 混合 / < 60% 走本地 |
| **N 判定率** | JEV 判 N 的比例 | 对比 mimo 的 93%，若显著更低说明 JEV 更有区分度 |
| **Brier** | 用 `calibration.py` 的算法，拿 JEV 的 probabilities | 需优于 mimo 的伪概率 |
| **中文失败模式** | 人工抽检 20 条，看是否系统性误判 | 无系统性偏差 |

### 3.3 成本估算

```
219 + 50 = 269 条样本
每条 state ≈ 2000 token（证据 + 8 假设）
总输入 ≈ 540k token × $0.042/Mtok ≈ $0.023
```

**两美分。** 这是整个方案里性价比最高的一步。

### 3.4 决策树

```
Phase 0 结果
├─ C/I 一致率 > 80%  → 走 API（Phase 2 直接接，跳过 Phase 1）
├─ 60% ~ 80%         → 混合模式（JEV 做初筛，低置信转 mimo 复核）
└─ < 60%             → 走本地复刻（Phase 1）
```

**注意**：官方文档提到 JEV 的 `confidence` 字段是**分布集中度的归一化**
（`c = (P_max − 1/K)/(1 − 1/K)`，来自第三方架构逆向），**不是正确性估计**。
做阈值分流时应基于 `probabilities`，不要用 `confidence`。

## 4. Phase 1：本地复刻（1~2 周）

仅在 Phase 0 判定「中文不可用」时启动。

### 4.1 数据问题（这是真正的瓶颈）

**现状盘点**（实测 `data/hypotheses/ach_matrix.json`）：

```
证据总数        388 条（82% 含中文）
总判定数        3104 条
判定码分布      N: 2885 (93%) | C: 111 | I: 108
有效 C/I 样本   219 条  ← 训练可用量
note 字段       3102 条有实质中文内容
```

**问题一：219 条训不出模型。** 且分布极不均：

| 假设 | C/I 样本数 |
|---|---|
| 全球能源转型加速导致传统能源需求骤降 | 79 |
| 全球能源供应格局重塑导致大国竞争 | 45 |
| AI 技术成本上升触发宏观经济波动 | 33 |
| AI算力与关键材料短缺限制商业化 | 28 |
| 台海冲突升级风险 | 19 |
| 美加贸易摩擦升级引发供应链重构 | 8 |
| 东亚三国现代化进程趋同 | 6 |
| 中国社保走韩国老路 | **1** |

**问题二：标签质量存疑。** 这 219 条 C/I 是 mimo 拍的，不是金标准。
直接拿来训练等于把现有偏差固化。

### 4.2 解法：用中文 NLI 打底

**关键洞察**：`CMNLI`（中文自然语言推理）与 ACH 的 C/I/N **结构同构**：

| CMNLI | ACH | 含义 |
|---|---|---|
| entailment | **C** | 前提蕴含假设 → 证据与假设预期一致 |
| contradiction | **I** | 前提与假设矛盾 → 证据与假设相斥 |
| neutral | **N** | 无关 |

CMNLI 有 **40 万+** 中文训练样本（`hfl/cmnli`，CLUE 榜单数据集，已验证可访问）。

**训练策略：两阶段**

```
阶段 A（打底）：CMNLI 40 万条 → 学会中文的「一致/矛盾/无关」判断结构
阶段 B（域适应）：ACH 219 条 C/I + 采样 N → 适配到情报分析领域
```

阶段 B 的样本量小，但因为是**域适应**而非从零学习，219 条 + N 采样是可行的。

**⚠️ 风险提示**：ACH 判定比 NLI 难 —— 它需要世界知识
（「中国社保政策」vs「谋杀案新闻」的相关性判断不是纯文本蕴含）。
0.6B 模型能否泛化是**未知数**，需要在阶段 B 后立即验证。
若泛化失败，退路是加大模型（4B/8B）或退回 API。

### 4.3 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 复刻框架 | **`jaredpalmer/kev`**（669★, Apache-2.0） | 唯一有完整训练代码的复刻；LoRA + pointer head；官方 SDK 改 base_url 即兼容 |
| 底座模型 | **`Qwen/Qwen3-0.6B`** | 官方称支持 100+ 语言（含中文）；kev 已验证 Qwen 系列可用 |
| 备选底座 | `Qwen/Qwen2.5-0.5B` | kev-0.5b 的原配底座，但 HF 标签仅 `en`，中文需实测 |
| 训练硬件 | **本机 RTX 3060 Ti 8GB** | 已验证 torch 2.13.0+cu126 + CUDA 可用；kev-0.5b 量级足够 |
| 云端备选 | H100（Modal） | kev 官方 4B/8B 配方在单张 H100 上 40~70 分钟 |

**不选 `wfzyx/von` 的原因**：它的底座是 ModernBERT，HF 语言标签 `['en']`，
是**英文单语模型**，中文语料直接废。

**不选 `zhengxuyu/litjev` 的原因**：它免训练（直接读 Qwen 输出头），
但 README 自述 "Probabilities are **not calibrated** by default" ——
正好丢掉你最看重的校准能力。

### 4.4 训练配置（参照 kev）

```
LoRA:        rank 16, alpha 32, dropout 0.05
target:      q_proj k_proj v_proj o_proj gate_proj up_proj down_proj（全部层）
Head:        指针头，把 <decide> 位置表示 与 选项隐状态比对 → softmax
Loss:        Cross-Entropy + Brier（联合，Brier 保证校准）
校准:        temperature scaling（kev 实测 T≈1.47，ECE 0.065 → 0.031）
```

### 4.5 数据格式（kev 兼容）

```json
{
  "state": {
    "evidence": "（领导）中国男子因谋杀研究生而被正式逮捕",
    "hypothesis": "东亚三国现代化进程趋同",
    "falsification": "（该假设的证伪判据）"
  },
  "questions": {
    "consistency": {
      "type": "choice",
      "instructions": "这条证据与该假设的预期是否一致",
      "criteria": {
        "consistent": "证据支持假设的预期",
        "inconsistent": "证据与假设的预期相斥",
        "neutral": "证据与该假设无关"
      },
      "label": "neutral"
    }
  }
}
```

## 5. Phase 2：集成（3 天）

### 5.1 两种接入路径

| 路径 | 方式 | 是否受 SSRF 护栏限制 |
|---|---|---|
| **API** | `POST https://api.typesafe.ai/v1/systemone` | 需加白名单（3 处） |
| **本地** | 进程内直接调用 kev 的 `DecisionModel` | **不受限**（无 HTTP） |

**本地路径的关键发现**：kev 的 `kev/model.py` 暴露 `DecisionModel` 类，
可直接 `from kev.model import DecisionModel` 进程内调用，**不需要起 HTTP 服务**。

这绕开了你项目的硬约束 —— `local/analyze.py` 的 `_safe_ai_post` 会拒绝
loopback/私有地址：

```python
if ip.is_private or ip.is_loopback or ip.is_reserved or ip.is_link_local or ip.is_multicast:
    raise ValueError("endpoint resolves to forbidden address: " + str(ip))
```

若起本地 HTTP 服务（`127.0.0.1:8009`），**必然被这条护栏拦下**。
进程内调用是唯一干净的解，**不要为了接本地模型去削弱 SSRF 守卫**。

### 5.2 改动清单

| 文件 | 改动 | 风险 |
|---|---|---|
| `local/ach_matrix.py:115-148` | `ai_diagnose` 改为调 JEV/本地模型；删掉 JSON 括号扫描解析器 | 中 |
| `local/ach_matrix.py:150-167` | `record()` 的 LR 改为代码推导 | 低 |
| `local/analyze.py:17` | `AI_ALLOWED_HOSTS` 加 `api.typesafe.ai`（仅 API 路径） | 低 |
| `tools/jev_probe.py` | 新建（Phase 0 探针） | 无 |
| `data/hypotheses/ach_matrix.json` | **不动**（向后兼容，只新增字段） | 无 |

### 5.3 note 字段的处理

**现状**：`note`（诊断理由，≤40 字）3102/3104 有内容，但**仪表盘不渲染**
（`gen_dashboard.py:558-600` 的 ACH 面板只用 `posterior`/`support`/`refute`）。

**决策**：JEV 生成不了 note，但 `export_markdown` 的诊断矩阵表**只显示 code+lr**，
也不读 note。所以 **note 可以安全丢弃**，无需混合调用。

若后续需要理由，走生成层单独补（一次 LLM 调用生成 8 条理由，成本远低于现在）。

## 7. 立即可以做的事（不依赖任何外部条件）

按性价比排序，**第 1 项现在就能做**：

1. **改造 `ai_diagnose` 为两段式门控 + 8 独立问题**（§2.1、§2.3）
   —— 不接任何新模型，纯结构优化。预期效果：诊断量下降、信噪比上升。
2. **LR 下沉到代码**（§2.2）—— 消除伪概率，为校准管道准备真概率。
3. **申请 JEV key**（`console.typesafe.ai`）—— 免费，等待期间不阻塞。
4. **写 `tools/jev_probe.py`**（Phase 0 探针）—— key 到位即可跑。

## 8. 结论

- **不要跳过 Phase 0 直接做本地复刻。** 两美分能证伪的假设，不值得花两周去赌。
- **本地复刻技术上可行**（kev + Qwen + CMNLI），但受限于你的标注数据量，
  应作为 API 路线失败后的备选，而非首选。
- **最有价值的改动与 JEV 无关**：拆问题、LR 下沉、两段式门控 —— 这三项现在就该做。
